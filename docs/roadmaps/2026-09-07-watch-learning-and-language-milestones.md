## 融合方式

以手表为贯穿项目，每一步同时留下三种结果：看得懂的电路解释、可复查的设计或操作、可用于 CoHDL 的需求样例。先用现有语言完成硬件步骤；语言特性落地后，再把已验证电路改写成对应的复用形式并检查等价性。

| 路线选择 | 收益与代价 |
| --- | --- |
| **推荐：demo → 小板闭环 → 手表开发原型 → 紧凑主板** | 每步都有可观察结果；新语言能力由真实需求验证，学习可以持续推进 |
| 从零直接画紧凑手表主板 | 更早面对最终外形，同时引入封装、射频、电源、固件和装配问题，定位失败的成本高 |
| 先完成全部语言能力再设计手表 | 语言实验更集中，但实板反馈来得晚，也推迟 PCB 学习 |

手表是语言能力的实际使用项目；原 roadmap 的十路 DC/DC 和 LED 链继续承担独立、容易核对的语言验收。手表按功能需要选择电路，十路 DC/DC 无需放进手表。

## 语言研发从手表获得什么

### M1：模块边界先由电路说明

手表分为 `power`、`controller`、`display`、`sensors`、`ui`、`debug` 六个源文件或功能区域，由顶层显式组合。接口表应同时记录连接信号、供电电压域、方向/驱动责任和上电要求；当前语言表达不了的条件先作为文档事实。

先复用现有 [被动元件 helper](../../lib/passive/src/circuits.cohdl)，再做同级功能区实验。已有 `decoupling_100n(vdd: Pin, gnd: Pin)` 可展开真实电容，但固定容值和额定值不适用于任意电源 pin；应按资料选择 helper。它的 `#[bypass]` 提示也不证明电容在 PCB 上足够靠近目标 pin。

重点观察：独立定义电源与 MCU 后，顶层能否合理连接；函数内部输出能否清楚暴露；修改调用是否影响实例路径和 design.lock。只有可运行样例暴露了缺口，才在 `fn` 输出接口与一等 `subdesign` 之间做语义决策。电路展开复用与整块 PCB 布局复制分别验收。

### M2：先用最小样例验证编程，再迁入手表

语言 PR 继续用 LED 链和十路 DC/DC 验证循环、索引、边界与独立实例。手表只在真正相同的按键/状态灯通道或规则化连接器、测试点上使用它。不同电源域、不同容值、不同布局约束的去耦网络不能只因外形相似就统一成一条循环。

当前数组已经支持，`for`、计算索引、常量算术与 fn 返回值尚未支持。学习材料中的未来语法必须标为提案，不能作为当前可执行教程。新旧写法比较规格和 pin-to-net 分区；相同来源和依赖的重复构建另查字节稳定性。

### M3：用手表检查配方的可迁移范围

首个语言配方仍按总 roadmap 做受限的 12V→5V、500mA DC/DC。手表电源输入随电池状态变化，显示和逻辑也可能有不同电压及时序要求；应另选适用的 buck、boost、buck-boost 或 LDO 配方，不能仅修改三个数字就复用原拓扑。

手表侧的结果包括：电源树、工作模式、峰值/平均负载、转换效率条件、充电与系统负载分配、选定阻容及容差。AI 负责资料和解释，经核对的公式和选料规则进入版本化领域库，离线构建保持确定。充电设置按选定电芯和充电芯片的资料确定，不能照抄 demo 的电流参数。

### M4：优先捕获实际遇到的电气错误

从 SF32 的电压域、显示供电和工作时序开始建立正反例：错误电压接入、所选 part 工作范围不满足、只有绝对最大值却没有工作条件、系统负载数据缺失。先说明事实从何而来、检查在哪个阶段执行，再决定契约形式。

电流与时序需要对应的负载/状态模型；仅有 net 名或额定值不足以判定。现有四条 residual DRC 保持既定边界，新增语义经 RFC 明确其类型检查、part 绑定后检查和无法判定时的处理。实物休眠电流、热表现与射频性能仍由测量验证。

## 手表平台的选择顺序

1. 优先复用现有 SF32 资料与接口经验做评估；它是目前最接近目标的本仓库参考，不等于已经选定最终 MCU。
2. 在画主板前选定实际可获得的显示模组，确认板侧连接器、尺寸、pin-1、供电、驱动接口与可运行的驱动程序。
3. 开发原型优先使用带既有天线实现的 MCU/BLE 模块或开发板先验证功能；进入自制 PCB 时优先评估可集成模块。若使用裸芯片，则把匹配网络、天线区域、叠层和射频实测列为单独设计任务。
4. 确认运动传感器驱动、地址和中断/复位接口，再选充电/系统供电方案与电池。先记录所需型号和资料，选型阶段再核验可购买性。
5. 原型成功后，按屏幕、电池、外壳和天线空间确定紧凑板框；保留可达的烧录、复位、关键电源测试点，以及测量系统电流的接入方式。

布局层数和线宽间距由选定器件、叠层及工厂能力决定。KiCad 官方教程也要求先配置板层与制造规则，再进行布局、布线和 DRC。[KiCad 10 入门教程](https://docs.kicad.org/10.0/en/getting_started_in_kicad/getting_started_in_kicad.html#board_setup_and_stackup)。

## Konnect 如何参与每一课

固定节奏：**讲解一小段 → 用户预测结果 → 操作一次 → 看图和查数据 → 用户复述 → 保存记录。** 一课集中在一个可观察的问题，例如“这个电容连接了正确网络，为什么还要移动它”。

- GPT-6 根据实际工程内容解释、选择工具并提出设计修改；Konnect 提供 KiCad 查询/编辑/CLI 检查能力。模型由客户端选择。
- 工具先从 `list_toolboxes` / `load_toolset` 发现，避免把不存在的工具写成课程依赖。图形定位不在工具能力内时，给出器件位号、坐标、网络和相应 KiCad 手动操作。
- 优先让用户亲自完成一次移动、布线和检查，再由 AI 处理重复操作。每次解释引用本板的位号、pin、pad 或网络。
- 每课保存练习对象与版本、一个问题、操作前后结果、解释和仍未检查的事项。只需 Markdown、工具输出和必要图像，暂不建设通用任务框架。
- 遇到源文件表达不顺，先记录最小复现和当前可用写法；按 M1–M4 顺序进入语言待办，不能让一次小练习自动扩大成编译器重构。

## 工程文件与检查职责

建议后续在 `/Users/zhangalex/Work/CoHDL/` 建立独立学习工程；本轮只保存路线文档，尚未创建这些目录：

```text
watch-lab/

  watch/         # CoHDL 源码、manifest、依赖锁和 design.lock
    out/         # 可重新生成的构建产物

  firmware/      # 原型固件、依赖版本、烧录与启动说明
  evidence/      # 对应源/板版本的检查、制造导出和测量
```

原生 KiCad demo 使用其 `.kicad_sch` 和 `.kicad_pro`；练习时复制完整项目及其库。进入自制 CoHDL 设计后，源码与锁文件描述逻辑，Explorer 用于查看，Konnect/KiCad 操作 PCB。

当前 CoHDL 没有原生 `.kicad_sch` 输出。原生 demo 的 ERC、原理图同步和制造 BOM 流程不能直接照搬到 CoHDL 工程：后者以 CoHDL BOM 为基础，独立核对最终 PCB 的实际器件、pin/pad 与网络。原型使用的离板屏幕、电池、模块和线束也要记录在装配清单中。

布线在 `pcb/` 中进行，不能在被构建产物清单管理的 `out/` 内进行。源修改后先生成候选板、比较器件与网络差异，再应用布局修改并重新检查；现阶段不假定有无损自动往返同步。参见 [原生 PCB 输出合同](../kicad_pcb.md)。

检查分三层记录：CoHDL 检查逻辑与已建模条件；KiCad 按当前规则检查保存后的实际板；收板后的测试检查物理行为。导出时同时记录 DRC 错误、未连接项、警告及排除项，不能靠屏蔽规则获得通过。学习阶段已有 demo 的问题按基线记录；自己的投板版本要处置与功能和制造有关的未决项。

## 第一课的具体安排

第一课只完成“连接正确工程，并看懂一条连接”。上次环境检查表明 KiCad CLI 为 10.0.6，但尚未建立 Konnect MCP/IPC 连接；开始实操时重新检查实际状态。

2. 建立 `sonde xilinx` 完整练习副本，打开对应项目和 PCB；确认 Konnect 查询到的项目路径与当前板一致。
3. 读取器件清单和网络，选择一个电阻及其相连 IC pin，展示原理图符号、封装与焊盘的对应。
4. 让用户指出电流/信号路径涉及的器件、网络和地；解释飞线与铜连接的区别。
5. 保存原始 DRC 基线与一页学习记录。第二课再执行一次移动或断线练习，观察新增问题并修复。
