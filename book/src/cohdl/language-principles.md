# 语言设计原则：怎样判断一个新功能

> **定位**：把已有设计哲学变成可以用于 RFC 评审的问题。前置：[设计理念](design-philosophy.md)；适用于比较新语法、复用方式和语言里程碑。本章及配套指南是归纳草案，不增加 Accepted 规则。

CoHDL 已有 Constitution、原则约束和演进治理。我们现在沉淀的是它们的应用方法：为什么选择某种设计，在什么条件下这个理由成立，怎样发现它破坏了别处的保证。

**核心哲学是：用少量可组合的概念表达电路，让表达能力建立在可检查的契约上。** 类型检查保护组合，显式输入帮助复现，稳定身份连接源代码和实物；每项“通过”都应有清楚的保证范围。

## 先记住三个取舍

正确性与机器可检验性（gradeability）先于书写便利。循环写起来再短，也必须检查展开后真实的引脚、元件与连接。严格性也有成本：限制应保护具体保证，并支持安全复用，而不是单纯使代码更难写。

复用既有机制先于另造平行概念。module、fn 和物理实例数组各有职责；[M2 草案](programming-proposal.md)的 for 应在它们之上重复操作。共同语义不要求所有东西使用同一语法，也不意味着机械照搬 Rust 或 EDA 的页面组织方式。

身份稳定与重复构建确定性分别验证。相同源码每次展开一致，仍可能在前插一个循环后把旧位号分给另一用途；这正是 M2 提议具名循环的理由。不过，具体命名语法尚待评审，不能由一句原则直接推导为唯一答案。

## 十条原则速查

| 编号 | 原则 | 提出功能时先问 |
| --- | --- | --- |
| P01 | 可检查的承诺与检查一起交付 | 哪个失败例证明检查实际执行？ |
| P02 | 在最早具备充分信息时检查结构错误 | 提前检查会不会破坏正常组合？ |
| P03 | 扩展共同语义，控制概念成本 | 现有概念为什么不够用？ |
| P04 | 语义依赖显式、可固定的输入 | 是否有隐藏状态或会漂移的依赖？ |
| P05 | 连接、默认和例外可追溯 | 结果由哪一处声明授权？ |
| P06 | 身份稳定单独验证 | 插入或重排后，还是那个器件吗？ |
| P07 | 抽象保留物理与输出责任 | 实际元件、物料和连接去了哪里？ |
| P08 | 诊断与工具属于语言契约 | AI 和人能找到并修复原始错误吗？ |
| P09 | 保证说明依据与覆盖范围 | 通过检查之后，究竟能宣称什么？ |
| P10 | 演进显式修改契约并记录理由 | 哪条旧规则改变，相关规范如何同步？ |

例如 required pin 的完整义务要等 design 组装后检查；`optional` pin 按声明规则可以不被提及。`nc` 只表达不连接，不能自行证明这个电路决策正确。这说明“类型优先”和“显式连接”都要结合具体契约理解。

可复现性的输入也要完整：除了源码、依赖和位号锁，还包括引用的板框 DXF 等构建资源。相同 `.cohdl` 配上被修改的 DXF，并不是相同构建输入。

## 用真实案例练习

[subdesign 两路 RC](subdesign.md)是 2026-09-08 的实现观察。2026-09-10 拉取最新 main 后确认 RFC-032 已接受，作为 M2 依据；此前因同编号旧 harness 提案而排除它的表述已撤回。该快照展示了容器与真实元件的区别：容器没有 BOM 行，内部的 R/C 仍各自存在；外部可通过规定的 place 路径放置内部元件，电气连接仍经过端口。

[Sonde 实验](sonde-case.md)展示了判定范围：语言检查通过、参考网表一致、物料绑定成功，是不同结论。将两个通道错误交换，可能仍满足语言结构规则；这时独立的需求对照才有用。

M2 则让我们评审候选机制：具名循环、共用整数/长度求值、空循环检查与展开上限分别保护什么，又增加多少成本？这些仍是提案，不因引用 P01–P10 就自动获得接受。
