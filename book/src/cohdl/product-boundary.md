# 产品与语言的边界：cohdl.ai 与 cohdl.dev

> **定位**：完整翻译 cohdl.ai 产品设计总览，并与[语言设计理念](design-philosophy.md)对照。原文状态日期为 2026-07-18；本章不核查或断言产品今天的上线状态。下文的产品建议与原文译文分开表述。

## 完整译文

### 这是什么

这是 **cohdl.ai** 持续演进的设计知识库。它采用“复杂产品一致性设计”（Coherent Complex Product Design）方法，围绕一个明确而聚焦的目标建立：

> **cohdl.ai 是“硬件领域的 Lovable”**，提供从想法到产品的体验。你描述想要的电路板，cohdl.ai 的代理在闭环中编写、编译、验证并修复设计，最终交给你真实、可制造的产出。

这份文档要把此前隐含的边界明确划出来：**cohdl.ai 是产品，cohdl.dev 是语言，两者不同。** cohdl.dev 是开源基础设施，包括语言、编译器和库注册服务，其基础设施角色类似 React／Next.js／Vercel。cohdl.ai 则是在这套基础设施之上构建的、有明确产品取舍、可以商业化的应用，类似于 Lovable 建立在 React／Next.js／Vercel 之上的应用定位。

随着 cohdl.ai 成长，这个知识库的每个部分都用于防止上述边界以及产品自身的一致性发生漂移。

它与同级的《CoHDL — 一致性设计知识库》相对应，后者负责治理语言。要理解 `.cohdl` 设计如何被验证，请读语言知识库；要理解 cohdl.ai 如何把自然语言想法变成这样的设计，并继续推进后续交付，请读这个产品知识库。

### 状态：2026-07-18

这是第一轮设计。根据 Products & Domains 的记录，cohdl.ai 仍处于早期：**域名已保留，尚未配置 DNS，也尚未构建产品。**

我们有意在开发开始前编写这个知识库，沿用语言知识库已经采用的纪律：先明确产品定位，避免每加一个功能才临时决定产品是什么。

| 编号 | 问题 | 已锁定的答案 |
| --- | --- | --- |
| 1 | 这是什么类型的产品？ | **以结果为导向的应用**，即“硬件领域的 Lovable”，而不是开发工具或语言官网。用户看到的体验是“想法 → 产品”，而不是“提示词 → 源代码”。 |

| 5 | 文档存放在哪里？ | 按工作区的归档规则，统一放在 Conol 工作区的 Project Overview 下，也就是这棵文档树中，不另建独立工作区。 |

### 知识库的组成

请按以下顺序阅读：

1. **产品宪章**：cohdl.ai 为什么存在、服务谁、不做什么、取舍优先级和硬性约束。
2. **概念模型**：Project、Turn、Verdict、Build 等产品层概念；有意复用 cohdl.dev 的概念，而不是另造一套平行概念。
3. **能力架构**：划分五个能力层，避免单项功能只获得局部优化。
4. **原则 → 约束映射**：把设计理念转化为可执行的设计规则。
5. **一致性矩阵**：分析新增能力会怎样影响系统的其他部分。
6. **决策记录**：保存创始决策，规定未来决策的记录格式，包括竞争定位的决策。
7. **演进治理**：让产品范围从“想法到原理图”，扩大到“想法到布局”，再到“想法到制造完成的产品”，同时保持统一定位。

### 日常运作循环

定义目标 → 推导原则 → 转化为约束 → 设计概念模型 → 梳理能力 → 通过提案评估功能 → 记录决策 → 检查整体一致性 → 治理目标变化 → 执行设计回归检查 → 继续迭代。

### 用一句话概括

我们不是在编译器前面放一个聊天界面，而是在构建一个持续演进的产品。它的每项能力都必须说明：它如何帮助用户沿着“想法 → 经过验证的设计 → 真实、可制造的硬件”继续前进；同时不能形成与底层语言竞争的第二套语言定义，也不能承诺我们尚未真正实现的交付阶段。

## 解读：三个系统各自负责什么

本文用 cohdl.dev 指代 CoHDL 的语言基础设施，用 cohdl.ai 指代建立在它之上的应用。域名在这里也是定位标签；上面的 DNS 描述仅是原文历史记录。

| 层次 | 文档中的职责 | 以“做一块手表主板”为例 |
| --- | --- | --- |
| **cohdl.ai：产品应用** | 将用户想法推进为设计和交付结果 | 与用户明确目标，组织生成、检查、修复和产物交付 |
| **cohdl.dev：语言基础设施** | 定义语言、执行编译与检查、提供库注册能力 | 表达 MCU、电源、显示等电路，依据已实现规则检查连接与规格并生成产物 |
| **Conol：通用代理运行时** | 提供会话、工具调用与记忆等运行能力 | 承载代理的工作过程，由产品层赋予硬件设计目标 |

cohdl.ai 同时依赖后两者。它不应为方便某个产品流程，复制一份语义不同的编译器；也不应为硬件设计重新分叉一套通用代理运行时。

“Lovable for hardware”在这里首先是产品定位比喻：用户表达目标，应用推动工作直至形成结果。本章没有核验 Lovable 的实际技术栈；原文的基础设施类比，也不能理解为 Vercel 的全部服务都是开源项目。

## 为什么“以结果为导向”比聊天界面多一层责任

如果用户要求手表主板，返回一段看起来合理的 CoHDL 源码，只完成了流程中的一个环节。产品还要让用户知道这份设计经过哪些检查、停在哪里、有哪些产物以及哪些条件尚未满足。

从这个定位可以推导出以下产品设计建议，**它们不是本篇已经实现的功能清单**：

- 需求不完整时，帮助用户补齐影响设计的条件，例如电源、外设接口或尺寸目标。
- 将某次源码、依赖、检查结果和构建产物对应起来，避免显示旧版本的“通过”状态。
- 发生错误后继续组织修复；无法自动解决时，明确指出缺少什么事实或决定。
- 根据实际完成阶段交付文件，不把源码存在、check 通过、build 成功或制造准备完成混为一个状态。

“用户不必从写代码开始”也不意味着隐藏源码。可查看、可审阅的 CoHDL 源码有助于信任和学习；产品定位要求的是交付不止于源码，而不是禁止展示源码。

## 哪些需求归语言，哪些归产品

这篇文档的边界可以直接用于整理我们的路线图：

| 需求 | 主要归属 | 原因 |
| --- | --- | --- |
| `fn`、模块、数组、单位、引脚义务的语义 | cohdl.dev | 决定源码含义和编译器如何判定，应该保持一个权威定义 |
| 标准化器件模型、part 数据与语言级契约 | cohdl.dev 的语言／库体系 | 不应让同一源码在不同应用里得到相互矛盾的含义 |
| 引导用户描述板子、解释错误、组织修复步骤 | cohdl.ai | 决定用户如何完成任务 |
| 项目页面、版本与产物展示、交付流程 | cohdl.ai | 属于产品体验和工作流；具体设计仍需后续定义 |
| 通用会话、工具调用、记忆机制 | Conol 运行时 | 属于可共享的代理基础设施 |

产品可以检查需求是否完整、是否缺少交付文件等工作流条件；这与另造一套 CoHDL 类型系统是两件事。发现语言契约不足时，应把问题和反例交给语言体系解决，而不是在聊天界面里暗中修改语言的有效性定义。

## “可制造的产出”与 MVP 之间需要明确门槛

原文开头给出了“真实、可制造的产出”的产品目标，但创始决策将 MVP 限定为网表、BOM 和**部分布局**。这是需要在交付定义中明确衔接的两种表述：

**网表、BOM 和部分布局本身，不能无条件证明已经可以直接投产。**

一方面，提供可制造文件与代用户完成实际制造并不相同；后者完全可以放在路线图里。另一方面，如果布线或必要的制造检查、生产文件还未完成，就需要如实标记为已验证设计或布局起点，不能因为愿景写了“可制造”便宣称该阶段已经完成。

这里不是要求 MVP 立刻覆盖所有阶段，而是建议分别定义交付状态及其证据。例如“已验证”需要指明检查了什么；“可交给后续布局”与“已具备制造交付条件”需要不同的验收条件。具体门槛应由产品设计与所支持的制造流程定义，本篇总览没有列出完整规则。

## 用 Sonde 实验理解产品应怎样报告结果

我们实际得到的是：

- 完整 25 实例的连接模型通过 check，与参考网表和既有 PCB 焊盘的静态连接对应一致。
- 完整 build 因缺少 part 绑定而报出 25 个 E801。
- 另一个两元件 RC 对照构建成功；它不代表整块 Sonde 已完成物料或制造准备。

因此，将来 cohdl.ai 若处理同样的情况，合理的状态说明应类似：**“连接模型已核对；完整构建尚缺物料绑定，暂未生成该板的生产网表和 BOM。”** 它需要继续推动缺失信息的补齐，而不是只展示一个成功标记。

这是一条从实验推导的产品建议，不表示 cohdl.ai 已经实现了这些页面或流程。我们本次使用的是 Codex、Konnect 和 CoHDL 的学习环境，也不能据此声称已经完成 cohdl.ai 与 Conol 的运行时集成。

你的“demo → 手表原型 → 手表主板”课程可以持续提供这种证据：哪些地方需要语言能力，哪些地方只是产品流程不清晰，哪些地方必须依靠实际测量。M1–M4 继续治理语言能力；面向用户的需求整理、版本展示和交付引导则属于产品层，二者可以配合推进。
