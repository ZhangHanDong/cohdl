## 为什么保留标签，代价又是什么

以拟议的 `for links: n in 0..(leds.len - 1)` 为例，`links` 标识这段生成连接的操作。重复调用 fn 时，循环中还可能产生真实器件，标签可以帮助它们在移动整段循环后保持身份。数组本身仍用原来的名称；`links` 不会变成可放置的一组 LED。

本轮比较了三种做法：

| 做法 | 得到什么 | 需要付出什么 |
| --- | --- | --- |
| 所有循环有标签：本轮建议 | 一个循环头规则；增加 helper 时不用再改变循环的命名方式 | 纯放置循环也要取名，尽管器件身份并不依赖它 |
| 所有标签可省略 | 简短；相同输入仍能得到确定结果 | 自动序号会受插入、重排影响，后来补标签也可能改变生成器件的路径 |
| 只允许 layout 内循环省略标签 | 放置已有器件时更简短，也不需要分析 helper 的效果 | 循环头是否合法取决于所处上下文；移出 layout 时要补标签 |

后两种不是错误设计。本轮建议先用统一有名形式，是在编写成本与身份/工具契约数量之间的取舍，不能说“没有标签就无法保证确定性”。标签也不能修复同一次迭代内部 fn 调用序号变化的问题。

LED 级联、十路 RC 和嵌套 FilterBank 都保持已有的对象接口。需要单独移动第七路电容时，仍通过具名 `channels[6].c` 的布局路径操作；循环标签不替代 subdesign。

## 区间不能只看符号相似

半开循环 `0..N` 表示 0 到 N−1；包含末端 fan-out `0..=(N - 1)` 选中同样的下标。一条 fan-out 为一条网增加成员，而循环可以建立多条网；这种电气区别并不决定该用哪种端点符号。

本轮建议保留两种已有/拟议约定，减少新增选择器规则。代价是读者仍要区分 `..` 与 `..=`。增加半开 fan-out 的备选方案也已具体列出：保留旧写法，明确步长、空选择、错误和 fmt；不能只加一种标点而让边界行为悬空。

当前编译器的实测还有一个细节：长度为 3 时，`arr[0..=3 step 2]` 只选中 0、2，因此可以通过；`arr[0..=3]` 会选中越界的 3，因此失败。检查实际选中的下标，与要求写出来的终点必须在数组内，是不同规则。M2 不能在不披露的情况下把后者加进去。

使用真实 lexer/parser 对 `lib/` 清点的结果是：60 个包、162 个源码文件，解析错误为零；只有两个非泛型 fn 定义，没有 subdesign 定义。清单位于 `docs/reviews/evidence/2026-09-12-m2-declaration-inventory.json`。零个 subdesign 定义只描述这份库语料，不表示语言没有该功能；[RC 实操](../course/03-rc-workflow.md)已有使用 subdesign 的实际证据。

因此，后续全库新旧检查都通过，也不能独立证明泛型/subdesign 的检查正确。准备计划已经补上单独的针对性语料要求，覆盖未调用定义、参数传递、端口、重复名称与环检查阶段。本轮记录的是解析与输入清单，尚未验证依赖，也没有完成新旧声明检查器的兼容性审计。
